# Стандарты кода и документации

Обязательны для нового и изменяемого Python-кода, проверок, конфигурации и
документации проекта. Задание PDF и ограничения замороженных данных сохраняют
приоритет в предметной области. Этот файл — единый источник правил разработки;
`AGENTS.md` содержит обязательную ссылку на него.

## Простой и читаемый код

- Использовать Python 3.11 и uv; зависимости добавлять только через `uv add`
  или `uv add --dev`, с объяснением назначения в документации.
- Предпочитать обычные функции и понятные `dict`, `list`, `tuple`, `set`.
  Для однократного действия достаточно функции; отдельный класс не нужен.
- Пользовательские классы вводить только при конкретной необходимости
  управлять состоянием или инвариантами, которую функции решают хуже.
  Объекты pandas, NetworkX и PuLP использовать по назначению библиотек.
- Сохранять плоскую структуру небольших предметных скриптов. Выделять общую
  функцию, когда она устраняет реальное повторение или делает расчёт понятнее.
  Абстрактные базовые классы, фабрики, универсальные движки, плагины и
  конфигурацию на гипотетическое будущее не добавлять.
- Давать переменным и функциям имена, объясняющие предметный смысл.
  Единицы отражать в именах: `distance_km`, `duration_min`, `cost_rub`.
  Короткие индексы допустимы внутри очевидной математической формулы.
- Предпочитать явные циклы сложным вложенным comprehension и цепочкам lambda.
  Функция должна выполнять одну понятную задачу; не вводить произвольные
  ограничения длины, мешающие чтению математической модели.
- Входы и результаты передавать явно. Загрузку файлов, запуск решателя и запись
  результатов выполнять из `main()` под `if __name__ == "__main__":`.
  Импорт модуля не должен запускать оптимизацию или менять файлы.

## PEP 8 и форматирование

- Строго следовать PEP 8: отступы по четыре пробела, код в UTF-8,
  `snake_case` для функций и переменных, `UPPER_CASE` для констант.
- Максимальная длина строки кода — 79 символов; комментариев и docstring —
  72 символа. Длинные выражения переносить внутри скобок; импорты группировать
  как стандартная библиотека, внешние зависимости, локальные модули.
- Идентификаторы писать по-английски; комментарии, docstring и Markdown —
  по-русски, как принято в проекте.
- Использовать Ruff для проверки стиля, имён, импортов и ошибок Python;
  `ruff format` — для единого оформления. Проверка форматирования не заменяет
  линтер: оставшиеся длинные строки нужно исправлять вручную.
- Читаемость, уместность абстракций и объяснение шагов проверять вручную:
  автоматические инструменты не проверяют весь PEP 8 и смысл программы.

## Комментарии, docstring и типы

- Каждая многошаговая функция должна содержать короткий комментарий перед
  **каждым логическим этапом**: что происходит и зачем. Нумерация помогает
  сопоставить реализацию с алгоритмом. Не комментировать каждую очевидную строку.
- Добавлять краткий docstring к модулю и функциям. Для нетривиальной функции
  описывать входы, результат, единицы, допущения и значимые ошибки.
  Однострочному вычислению достаточно однострочного docstring.
- Аннотировать аргументы и возвращаемый тип всех новых и изменённых функций,
  включая `main() -> None`; проверять их через mypy.
- Начинать с встроенных типов и простых псевдонимов. Дополнительные схемы типов
  вводить только если они делают реальные входы/выходы понятнее.
- Не подменять типизацию повсеместным `Any`, фиктивными `cast` или общими
  отключениями проверки. Для действительно нетипизированной внешней библиотеки
  допустимо узкое исключение с объяснением; сначала проверить доступные stubs.
- Проверять ожидаемые ошибки данных и решателя явно. При отсутствии допустимого
  incumbent возвращать понятный статус, а не трактовать LP-значения как план.
  Не скрывать ошибки через `except Exception: pass` и похожие конструкции.

Пример оформления многошаговой функции:

```python
def annual_capacity(
    seats: int,
    flights_per_day: int,
    operating_days: int,
) -> int:
    """Вычислить число доступных пассажирских мест за год."""
    # 1. Перевести суточное число рейсов в годовое.
    annual_flights = flights_per_day * operating_days

    # 2. Перевести рейсы в места с учётом вместимости дрона.
    return seats * annual_flights
```

## Принципы Karpathy

Применять четыре принципа из указанного пользователем
[karpathy-guidelines](https://github.com/multica-ai/andrej-karpathy-skills/blob/main/skills/karpathy-guidelines/SKILL.md)
(проверено 25.10.2026; это общественная формулировка по наблюдениям Karpathy):

1. **Обдумать до реализации.** Явно назвать допущения и существенные варианты.
   При неоднозначности, меняющей результат, описать вопрос и уточнить его;
   независимую понятную работу продолжать. Предлагать более простое решение.
2. **Начать с простоты.** Реализовать минимальный достаточный вариант задачи.
   Добавлять только необходимое поведение, без абстракций ради одного вызова
   и без неподтверждённых требований на расширяемость.
3. **Менять прицельно.** Каждая правка должна относиться к текущей задаче.
   Убирать ставшие ненужными из-за неё импорты и переменные; сторонние проблемы
   фиксировать отдельно. Существующий стиль учитывать в рамках PEP 8.
4. **Работать до проверяемого результата.** Для каждого этапа определить
   результат и способ проверки; выполнить проверку и исправить найденные
   проблемы. Для ошибки воспроизвести нарушение, для рефакторинга сравнить
   поведение до и после. Не завершать этап заявлением без подтверждения.

## Документация и результаты

- `README.md` описывает запуск; `PROJECT.md` — предметные решения и статус;
  этот файл — стандарты; `IMPLEMENTATION_PLAN.md` — последовательность работ.
  Подробный алгоритм документировать рядом с его кодом, не копировать повсюду.
- В математической постановке определять переменные, единицы, ограничения,
  временной масштаб и целевую. Отделять требования PDF от учебных допущений.
- При изменении поведения обновлять соответствующую документацию в той же
  задаче. Не объявлять старые численные результаты актуальными после изменения
  модели; сохранять исходные результаты и писать новые в отдельный каталог.
- В артефактах расчёта сохранять ID пунктов, входные версии/хеши, параметры,
  seed, статус решателя, лимит времени, время расчёта, incumbent и границу
  с формулой разрыва. Подписи, таблицы и графики должны указывать единицы.
- Формулировать выводы в пределах доказательств: найденный план не равен
  оптимуму; агрегатная перевозка не равна подтверждённой расписанием;
  чувствительность синтетического спроса не равна прогнозной точности.
- В итоговом отчёте фиксировать использование ИИ и допущения. Для новых
  зависимостей объяснять назначение и изменение воспроизводимого окружения.

## Обязательные проверки

Из корня репозитория, после настройки окружения через `uv sync --locked`:

```powershell
uv run --locked ruff check .
uv run --locked ruff format --check .
uv run --locked mypy
```

- Запускать все три команды после правок кода и конфигурации и перед передачей
  завершённого этапа. Для документации проверить также ссылки и соответствие
  команд реальному интерфейсу. Показывать коды завершения и оставшиеся ошибки.
- Исправлять замечания в рамках текущей работы. Если первичное внедрение
  проверок обнаружило старые нарушения, записать полный исходный список и
  устранять его отдельным этапом; до этого проект не считать прошедшим проверки.
  Новые изменения не должны добавлять нарушения. Режим первичного аудита
  не является разрешением оставлять ошибки в завершённом рефакторинге.
- Правила Ruff и mypy не ослаблять ради зелёного результата. Исключения могут
  быть только точечными, с объяснением причины и проверкой актуальности.
- Для исправлений расчётов использовать небольшие проверки математических
  инвариантов, например переноса бюджета, асимметричного спроса и пересадки.
  Проверять смысл результата, а не точное повторение реализации.
- После правок решателей выполнить small-прогон и сравнение с сохранённой
  целевой при тех же условиях; при изменении модели объяснить несопоставимость
  старой и новой цели. Для замороженных входов проверить неизменность хешей.
- Команды загрузки и регенерации данных не являются способом проверки стиля.
  Замороженные `data/raw/`, `data/processed/` и параметры не перезаписывать.

Dev-зависимости: Ruff проверяет стиль и форматирование, mypy — типы;
`pandas-stubs`, `types-requests`, `types-networkx`, `scipy-stubs` описывают
внешние API для mypy. Эти пакеты не меняют математическую модель.
